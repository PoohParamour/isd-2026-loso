RESTful API Basics
ตัวอยาง การกําหนด path
พนักงานหลายคน:
GET https://api.abc.com/v1/employees
ใช Plural หรือ Singular nouns (จะเลือกใชอะไรก็ตาม ก็ควรใหมันสอดคลองกับ APIs ทั้งหมดที่มี)
แบบการกรอง:
GET https://api.abc.com/v1/employees?year=2011&sort=desc
GET https://api.abc.com/v1/employees?section=economy&year=2011

[PAGE 12]
ใชสัญลักษณเทากับ (=) สําหรับเทคนิคที่ใชเปรียบเทียบขอมูลที่เทากัน และสําหรับการ
Advanced Filtering
ตัวอยาง:
?filters=creation_date >= 2001-09-20T13:00:00 and creation_date <= 2001-09-21T13:00:00 and 
post_code = 3000
จะแสดง collection ของ resources เมื่อ creation_date อยูระหวาง 2001-09-20 1pm และ 2001-09-21 1pm และ 
post_code คือ 3000
ตัวอยาง:
?last_name=Johnson&date_of_birth=1999-12-31
จะ Filter ขอมูล ดวย attribute last_name ที่เทากับ Johnson และ date_of_birth เทากับ 1999-12-31

คําแนะนําการออกแบบ API Versions
โดย API version ควรจะ กําหนดไวอยูเสมอ (เชน คาเริ่มเปนเวอรชันลาสุด)
โดย API version ควรจะ ระบุดวย 'v'
ถาผูใชงานพยายามเขาถึง API ดวยการไมระบุเวอรชัน ดังนั้นเขาก็ควรไดรับขอความผิดพลาดตอบกลับ 404
ถาผูใชงานพยายามเขาถึง API ดวยการไมระบุ resource (เชน GET .../api/v1) การตอบกลับอาจจะประกอบดวย
ขอมูลพื้นฐานเกี่ยวกับ API (เชน ชื่อ API, และรายละเอียดอื่น ๆ)
โดยอาจจะมี API version หลายอันไดตัวอยาง:
.../api/v1/articles
.../api/v2/articles

[PAGE 19]
รายละเอียดของ APIs Version เปนไปตาม semantic versioning:
{MAJOR}.{MINOR}.{PATCH}  2.5.3
เวอรชันแรกของ API ตอง เริ่มตนดวยเวอรชัน MAJOR เปน 1
ใชแนวทางตอไปนี้เมื่อเพิ่มหมายเลขเวอรชัน API:
MAJOR เวอรชัน เมื่อทําการ incompatible ของการแกไข API
MINOR เวอรชัน เมื่อเพิ่มฟงกชันใน backwards-compatible หรือคุณสมบัติอื่น ๆ
PATCH เวอรชัน เมื่อทําการ backwards-compatible การแกไขขอพกพรอง
